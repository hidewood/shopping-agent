# 智能购物 Agent 实验报告

## 1. 实验目标

本项目实现一个面向本地商品目录的购物 Agent。系统需要将自然语言购物需求转化为可验证的商品检索、约束校验、候选比较和购买建议，并能在多轮对话中保持状态而不让目录浏览污染当前购物任务。

## 2. 大模型使用方式

系统使用 DeepSeek API，但不让模型直接生成商品事实或直接决定数据库写入。每条用户消息由模型生成受限的结构化 `TurnPlan`，其中包含：任务目标（聊天、目录信息、商品信息、选择或交易动作）、目标对象、商品需求、目录操作和状态动作。

程序随后验证该计划的字段组合、枚举值和目录提示。模型未能返回合法计划时，系统会在无副作用前尝试一次协议修复；连接、认证、限流和超时错误则直接终止本轮，不以本地规则伪造模型理解结果。

## 3. Agent 工作流

```text
用户消息
  → DeepSeek：TurnPlan 语义规划
  → 契约校验 / 一次协议修复
  ├─ chat / none                 → 客服回复
  ├─ information / catalog       → 真实目录聚合
  ├─ information / product       → 商品 ID 详情或比较
  ├─ selection / catalog         → 状态归约 → 硬过滤 → 确定性排序 → 推荐
  └─ action / transaction        → 能力注册表检查
```

推荐执行阶段由代码承担可验证的事实操作：先过滤商品类型、预算、硬厂商和硬主题，再按“已验证偏好 → 价格从低到高 → 商品 ID”稳定排序。这样模型负责理解诸如“纽约风”“优先某厂商”“价位”等语义，工具负责保证商品、价格、标签和排序结果真实可复现。

## 4. 状态与工具设计

- `ConversationState`：以事件日志保存需求更新，通过 reducer 得到当前购物条件。
- `TaskContext`：独立记录推荐收集、已推荐、目录浏览、商品详情/比较和交易动作阶段，防止只读查询覆盖未完成推荐。
- `ProductRepository`：从 `products.jsonl` 读取 1,740 件商品，提供目录聚合、受控中英文值对齐、硬约束过滤和稳定排序。
- `RecommendationPolicy`：由代码决定何时信息足以推荐。模型可以给出追问文案，但不能在类型、主题、预算或厂商等条件已足够时无理由阻止执行。
- `CAPABILITY_REGISTRY`：订单、支付和取消订单被显式标记为未实现，系统不会假称已下单。

## 5. 提示词与安全边界

规划提示词要求模型只输出 JSON，且 `goal`、`target`、目录操作、状态动作和交易动作均为受限词表。目录规范值保留英文；中文表达通过受控别名或模型提供的、经目录验证的提示映射到规范值。未知或多义风格会保留 `unresolved` / `ambiguous` 状态，不能被伪装为已有商品或零结果。

## 6. 评测结果

对 `data/tasks.jsonl` 的 50 条公开任务进行了真实 API 评测。判定要求为：返回商品满足显式类型、主题标签、预算、严格厂商条件；当存在满足硬条件的优先厂商商品时，结果应优先该厂商；trace 必须记录确定性候选排序。

- 最终结果：50/50 通过，成功率 100%。
- 首轮结果：47/50 通过。
- 修正与复测：A023、A047 暴露模型把已充分需求误标为需要追问；修正为由 `RecommendationPolicy` 决定推荐资格。A035 为单次模型响应异常。三条复测均通过。

逐项结果见 [task-evaluation.md](task-evaluation.md)，机器可读 trace 见 [task-evaluation.json](task-evaluation.json)。

## 7. 人工核验

人工对话验证了：目录查询与购物任务隔离、跨品类新任务替换、硬主题与偏好厂商、确定性排序依据、商品详情与比较。对应记录与截图说明见 [representative-runs.md](representative-runs.md)。

## 8. 局限性

- 商品名称、标签和描述来自英文演示数据集，因此界面保留其原始英文信息。
- 当前交易动作仅完成协议和能力边界设计，未实现真实订单持久化与支付。
- 模型服务受网络与提供方时延影响；系统会记录错误类别并避免执行未经规划验证的推荐。
