# 智能购物 Agent 实验报告

## 摘要

本项目实现了一个面向离线电商商品库的自然语言购物 Agent。系统以 DeepSeek 为语义规划器：模型将用户当轮表达转换为受限的 `TurnPlan`，但不直接生成商品事实或决定最终商品；本地 Python 代码负责目录接地、硬约束验证、候选排序、会话状态迁移和结果解释。该分工使系统既能理解中英文自然语言，又能保证类型、预算、主题、厂商和商品详情均可由 `products.jsonl` 复核。

系统覆盖题目要求的需求理解、商品搜索、候选比较、约束检查、购买决策和结果说明，并实现多轮填槽、主动引导、状态隔离、无结果解释、显式组合方案、会话级收藏/模拟订单和真实交易能力边界。组合方案以行项目保存类别、数量和分别的主题条件：每件预算模式逐行检索，合计预算模式按数量计算组合总价。用户明确收藏或创建本地模拟订单后，系统仅保存相关商品的目录属性，作为后续排序的次级信号。商品库包含 1,740 件商品，其中 `mug` 与 `shirt` 各 870 件。本文中的历史测试结果与本轮新增回归分别标注，避免将不同运行条件下的结果混为一谈。经过工程化演进与后续"做减法"收敛，系统最终定型为一条轻量、单一的架构：以 LLM 语义归一化、`TurnPlan` 单轮规划、确定性检索排序与个性化推荐为核心，移除 RAG 向量检索、ReAct 循环与双模式切换，并对真实交易能力保持诚实边界。

**关键词：** 大语言模型；Agent；结构化规划；商品检索；多轮对话；约束验证；语义归一化

## 1. 任务要求与问题定义

题目要求构建一个可运行购物 Agent，完成需求理解、商品搜索、候选比较、约束检查、购买决策与结果说明；模型选择、提示词、工具编排和失败处理可自行设计，多轮对话和主动追问属于可选增强。本项目将任务转化为如下问题：如何让模型理解开放式购物表达，同时不让模型替代商品库事实和确定性决策。

数据集不提供训练集/验证集划分，仅提供商品库与 50 条公开模拟需求。每个商品含 `product_id`、`name`、`item_type`、`manufacturer`、`price`、`tags` 与 `description`。因此，本系统只把能够映射到这些字段的条件作为可验证约束；对“Disney 主题”等目录无法接地的硬条件，系统必须明确报告不可满足，而非生成看似合理的商品。

本项目的目标如下：

1. 将中英文自然语言转化为可审计的意图与需求增量；
2. 仅依据本地商品库返回商品事实、统计、详情和比较；
3. 支持用户逐轮补充类型、预算、主题和厂商，而不是要求一次输入完整条件；
4. 把聊天、目录查询、详情、比较、推荐和交易请求放入不同的受控路径；
5. 在模型输出异常、无匹配或能力未实现时安全失败，并保留可解释记录。

## 2. 大模型使用方式

### 2.1 调用配置与职责边界

系统通过 OpenAI 兼容 SDK 调用 DeepSeek API，`base_url` 为 `https://api.deepseek.com`。模型名由环境变量 `DEEPSEEK_MODEL` 配置；示例环境文件使用 `deepseek-v4-flash`，代码在未设置时默认 `deepseek-v4-pro`。调用温度固定为 `0.2`，超时和重试次数由 `DEEPSEEK_TIMEOUT_SECONDS` 与 `DEEPSEEK_MAX_RETRIES` 控制。连续两次瞬时服务错误后，进程级熔断器会在 `DEEPSEEK_CIRCUIT_BREAKER_SECONDS` 指定的冷却期内暂停新的模型调用；聚合记录调用次数、错误类别和延迟分位数，但不记录提示词或模型原文。

模型的唯一核心职责是生成**单轮声明式计划**：判断用户当前是聊天、查询、选购还是交易请求，并抽取需求增量及状态操作。模型不读取商品库、不计算商品数量、不选择商品 ID，也不生成未经验证的价格、厂商或标签。这样可将模型的开放语义能力与程序的可验证能力分离。

| 能力 | 由模型完成 | 由本地代码完成 |
| --- | --- | --- |
| 意图理解 | 解释中英文表达、判断本轮目标和需求增量 | 强意图信号预处理与计划一致性检查。 |
| 需求规范化 | 提出类型、主题、厂商、预算等候选含义 | 与目录规范值匹配，未知硬条件标记为不可满足。 |
| 商品事实 | 不生成 | 检索、计数、详情、比较、价格范围和标签统计。 |
| 推荐决策 | 不指定商品 ID | 硬过滤；当前轮显式偏好优先，会话偏好次之，价格与 ID 最后打破平局。 |
| 交易与本地模拟 | 可识别真实交易动作；不参与本地收藏/模拟订单决策 | 真实订单、支付和取消由能力注册表拒绝；收藏/模拟订单仅写入当前设备的会话本地状态。 |

### 2.2 结构化输出与失败处理

API 使用 `response_format={"type": "json_object"}` 要求模型返回 JSON 对象。原始响应先按 Draft 2020-12 的 `TURN_PLAN_JSON_SCHEMA` 校验：拒绝未知字段、错误的 JSON 类型，以及不在受限词表内的顶层枚举；兼容的历史 `intent` 计划仍按旧解析路径处理。随后 `TurnPlan.from_dict()` 继续校验字段组合，例如 `goal=selection` 必须使用 `target=catalog` 并携带需求，`goal=action` 必须使用交易目标和受限动作词表。

这不是“只靠提示词”的 JSON 约束：服务端 JSON 对象、本地 JSON Schema、Python 数据类的跨字段校验、强意图一致性检查和目录接地共同构成多层防线。本实现不依赖某个服务商的严格工具调用：即使未来更换到服务端 Schema 或严格工具调用接口，跨字段约束、授权证据和目录事实验证仍应保留在代码侧。

如果模型计划无效，系统只在尚未检索、尚未写入业务状态时进行一次无副作用协议修复；修复仍无效则返回带失败阶段和错误类别的 `service_error`，不会用本地猜测伪造推荐。模型健康指标和熔断状态只用于诊断与保护上游服务，不参与商品事实或推荐结论。

## 3. Agent 总体架构与工作流

![图 1：系统总体架构。模型输出计划，本地代码负责状态、事实和排序。](screenshots/architecture-ai.png)

系统由四层组成。

| 层次 | 组件 | 输入与输出 | 责任 |
| --- | --- | --- | --- |
| 交互层 | `app.py`、Streamlit | 用户消息、对话、商品卡片、Trace | 即时显示用户消息与加载状态；按“回复—条件—卡片—依据”呈现结果。 |
| 规划层 | DeepSeek、`TurnPlan` | 自然语言 → 受限 JSON 计划 | 识别语义，不产生商品事实。 |
| 编排层 | `ShoppingAgent`、`ConversationState`、`TaskContext` | 计划 → 受控路由 | 检查输入/计划、更新状态、决定澄清、探索或推荐。 |
| 数据与决策层 | `ProductRepository`、组合搜索器、偏好档案 | 需求 → 目录事实/候选/排序 | 目录接地、检索、统计、详情比较、无结果近似方案、可解释排序和组合价格校验。 |

### 3.1 主工作流

![图 2：主工作流及协议异常处理。](screenshots/workflow-ai.png)

一次完整回合按以下顺序运行：

1. 接收用户消息，先检查空输入、倒置价格区间等明确输入错误；
2. 提取商品 ID、比较词、目录查询词、交易词等强意图信号；这些词汇及中英文别名可由 `data/catalog_language.json` 扩展；
3. 对少量高置信场景直接处理，例如无类型的礼物请求、显式开放式直接推荐、活动选购中的预算补充或泛化“推荐一个”续接、同轮多类型购买的组合澄清、带每件或合计预算的显式组合方案、本地收藏/模拟订单，以及两类商品的并列价位查询；其余场景调用 DeepSeek 生成 `TurnPlan`。若模型服务临时不可用，基础问候可安全降级为固定提示；
4. 校验计划结构及其与强信号的一致性，必要时只修复一次；
5. 按计划路由到聊天、目录查询、商品详情/比较、选购、本地收藏/模拟订单或真实交易能力检查；
6. 若为选购，重放状态事件得到当前需求，接地为商品库规范值，执行硬过滤；排序时依次使用当前轮已验证显式偏好、会话级显式反馈形成的偏好分数、价格与商品 ID；
7. 输出主回复、筛选条件、商品证据及可展开 Trace。

图 2 展示的是进入模型规划的通用路径；第 3 步中的高置信直达分支会在模型调用前返回受控结果。无论走哪一条路径，模型输出都是“下一步做什么”的提议，而不是“商品是什么”的证据。所有对用户可见的商品事实都来自受控工具执行结果。

实现中，高置信分支的优先级也被固定：输入完整性、能力边界、本地收藏/模拟订单和无类型礼物请求在前；随后依次处理组合购买的待填槽续接、显式组合方案、同轮多类型购买识别、双类型只读价位查询，以及活动选购中的预算补充或泛化“推荐一个”续接；其余自由表达才进入模型规划。基础问候通常也交由模型处理，只有模型服务临时不可用时才返回不涉及商品事实的固定提示。显式组合方案以“组合方案 / bundle”等表述作为购买意图本身，因此“`马克杯和T恤，总预算20以内，给我组合方案`”不必重复“想买”也会进入受控组合路径。每件预算模式分别检索各行项目；合计预算模式在候选空间较小时穷举所有行项目组合，在空间较大时使用固定候选池和束宽进行有界搜索，并在 Trace 中标记所用策略。两种模式都由代码校验价格和数量，不让模型分配预算或选择商品。会话偏好只来自用户收藏或本地模拟订单中已选商品的厂商、标签和类别属性；它只能在已通过硬过滤的候选之间作为次级排序依据，不能放宽约束。因此“`mug 和 shirt 分别有什么价位？`”不会误入组合购买，而短句“推荐一个”只有在已有活动选购条件时才会复用该条件。这些规则只覆盖低歧义表达，不替代模型对一般自然语言的理解。

### 3.2 状态机与多轮填槽

![图 3：多轮选购状态、只读查询隔离与常规双类型购买澄清。](screenshots/state-lifecycle-ai-v2.png)

系统将会话状态分为三个层次：

- `ConversationState` 是会话容器，保存事件日志、待填槽问题、待填字段、最近只读查询上下文、组合购买临时槽位，以及当前会话的 `saved_product_ids`、`simulated_orders` 和 `PreferenceProfile`。本地操作缺少商品 ID 或订单编号时，还会记录待续接的本地动作，保证用户下一轮只输入 `P0005` 或 `SIM-0001` 也能回到原操作；
- `ShoppingRequirement` 保存“要买什么”：商品类型、预算、主题、厂商及其硬约束/偏好强度；它由事件 reducer 在检索前重放得到；
- `TaskContext` 保存“正在做什么”：活动任务、选购阶段、最近选中商品、候选列表和最近只读查询目标。

下表描述的是 `TaskContext` 的选购主状态机。`ConversationState.status=awaiting_user` 只表示本轮仍等待用户填写 `pending_fields`，并非额外的选购业务状态。代码中的 `recommending` 是硬过滤和排序前的内部判定；商品产生并完成核验后，持久化的选购阶段才写为 `recommended`。

| 当前状态/条件 | 触发输入 | 下一状态 | 系统行为 |
| --- | --- | --- | --- |
| 无商品类型 | `我想买礼物` | `collecting` | 只询问 mug 或 shirt，不要求一次补全所有字段。 |
| 已知类型、无细化条件 | `我想买一个马克杯` | `exploring` | 展示真实价格范围、常见主题和目录样例，主动提示可补充的筛选维度。 |
| 已知类型且有筛选条件 | `Ocean主题，预算20元以内` | `recommending` → `recommended` | 归约状态、接地、硬过滤、排序后返回推荐结果。 |
| 明确开放式选择 | `不限预算和风格，直接推荐一个` | `recommended` | 允许默认排序直接给出一个商品。 |
| 无候选 | `预算8元以内` | `no_match` | 报告无匹配，给出仅放宽一个条件的最近可达方案。 |
| 目录查询/详情/比较 | `有什么价位`、`介绍 P0005` | 保留原选购状态 | 以只读方式执行，不覆盖活动 `ShoppingRequirement`；后续带明确筛选条件，或仅说“推荐一个”时均可复用当前选购条件。 |
| 同轮多类型购买 | `我想买马克杯和 T 恤，预算20以内` | `collecting` | 不将两类商品错误合并为一个类别；先确认预算是每件上限还是合计预算。用户未明确要求组合时，仍可选择先处理其中一类。 |
| 显式组合方案 | `Ocean主题马克杯和Snow主题T恤，每件预算20元以内，给我组合方案` | `recommended` | 只在用户明确要求组合且给出可解析预算时触发。组合行项目分别保存类别、数量和硬主题；每件预算模式逐行过滤，合计预算模式搜索多行项目组合并按数量验证总价。 |
| 本地收藏/模拟订单 | `收藏 P0005`、`创建模拟订单 P0005` | 保留选购主状态 | 仅更新 `saved_product_ids`、`simulated_orders` 和偏好档案；缺少本地 ID 时状态机进入本地待填槽，后续单独回复 ID 可续接。订单状态标记为 `confirmed_local` / `cancelled_local`，不调用真实交易服务。 |
| 多类型只读价位查询 | `mug 和 shirt 分别有什么价位？` | 保留原选购状态 | 绕过单类型映射，分别返回两类商品的数量、最低价与最高价；不触发组合购买澄清。 |
| 新类型请求 | `改成 Snow主题T恤` | 新选购任务 | 使用 `replace` 清除旧类型、主题、预算和厂商。 |

选购需求的变化记录为事件；检索前由 reducer 重放这些事件得到当前 `ShoppingRequirement`。`TaskContext` 则保存当前任务阶段和最近只读查询上下文。每次任务状态更新都会在 Trace 中记录更新前后的任务、阶段、选中商品与候选 ID；只读查询在存在选购任务时显式标记为“保留选购状态”。因此，“想买 T 恤 → 查询 T 恤价位 → 预算低于 20”不会因中间目录查询丢失 T 恤条件，而明确换成马克杯或 T 恤时又不会让旧条件泄漏。

图 3 只描述选购任务的主状态迁移。模型协议异常和服务超时属于图 2 中的失败分支：本轮返回 `service_error`，不以猜测结果改写选购需求；连续瞬时服务错误会触发进程级短暂熔断。真实订单、支付和取消订单属于能力检查分支：返回 `capability_unavailable`，同样不产生交易状态，同时保留已有选购上下文。收藏和模拟订单则是与选购状态隔离的本地记录；它们只会形成可审计的弱偏好，不会改变硬过滤或调用外部服务。这样，选购状态机只承载可检索需求，异常处理、本地记录和未实现能力都不会混入推荐事实。

## 4. 提示词与工具设计

### 4.1 `TurnPlan` 提示词契约

系统提示要求模型仅返回一个 JSON 对象，核心字段如下。

| 字段 | 合法值/结构 | 作用 |
| --- | --- | --- |
| `goal` | `chat` / `information` / `selection` / `action` | 本轮目标。 |
| `target` | `none` / `catalog` / `product` / `transaction` | 目标对象。 |
| `requirement` | 类型、厂商、价格、主题、澄清信息 | 用户表达的需求增量，不含商品事实。 |
| `catalog_operations` | `count`、`list`、`price_range`、`group_by_tag` 等 | 只读目录查询允许的操作。 |
| `state_action` | `none` / `merge` / `replace` | 如何更新选购状态。 |
| `selection_mode` | `criteria` / `explicitly_open` | 区分带条件推荐与明确允许默认选择。 |
| `action` | 受限交易动作词表 | 只用于能力检查，不直接执行交易。 |
| `goal_evidence` | 本轮原文片段 | 为高风险动作保留用户授权证据。 |

提示词还给出“目录查询与选购”的对照例：`衬衫都有什么价位？` 是只读目录查询；`推荐一件 T 恤，预算 30 以内` 是选购。它要求把 `prefer`、`喜欢`、`优先`标记为偏好，而把明确类型、预算、主题和“必须某厂商”标记为硬约束。

以“`Ocean主题马克杯，预算20元以内`”为例，模型计划只描述用户需求增量，不含候选商品或商品事实。下例为字段完整性说明，空字段可在实际响应中为 `null`：

```json
{
  "goal": "selection",
  "target": "catalog",
  "requirement": {
    "item_type": {
      "raw_value": "mug",
      "constraint_strength": "hard",
      "catalog_hint": "mug"
    },
    "manufacturer": null,
    "price_constraint": {"operator": "<=", "value": 20},
    "concepts": [
      {
        "raw_value": "Ocean",
        "kind": "theme",
        "constraint_strength": "hard",
        "catalog_tag_hints": ["Ocean"]
      }
    ],
    "needs_clarification": false,
    "clarification_question": null
  },
  "catalog_operations": [],
  "state_action": "merge",
  "selection_mode": "criteria",
  "action": null,
  "goal_evidence": ["Ocean主题马克杯", "预算20元以内"]
}
```

随后，代码将 `mug`、`Ocean` 和价格上界映射至目录规范值，再完成筛选和排序；因此 `P0005` 等商品 ID 不属于模型计划字段，也不由模型指定。

提示词不能单独保证正确性，因此代码补充了少量高置信规则：识别商品 ID 的比较/详情/交易请求；解析中英文价格区间；识别 `Ocean主题` 等拉丁标签与中文后缀连写；以及对“单一类型 + 不限条件 + 直接推荐”的开放式请求直接进入推荐。这些规则只覆盖歧义较低的形态，常规自由文本仍交给模型规划。

### 4.3 解释设计

每轮 Trace 记录输入信号、模型计划、约束更新、状态归约、目录接地、过滤漏斗、候选比较、组合搜索策略和决策验证。模型调用另记录不含原文的耗时、错误类别和熔断状态。任务状态变化还会记录变更前后快照，方便核对只读查询是否意外覆盖了选购任务。界面不把全部内部 JSON 强加给用户：先用自然语言说明推荐原因，再显示已应用条件与商品卡片；在探索与推荐回复后，再给出由目录事实生成的下一步条件示例。需要时可展开核验记录。这使“为什么推荐这件商品”和“系统如何保证条件正确”分别对普通用户和评阅者可见。

### 6.3 会话偏好、组合搜索与本地状态

排序并不把“用户以前看过什么”当作事实条件。系统只在用户主动收藏商品或创建本地模拟订单后，记录商品的厂商、标签和类别计数；新的检索请求仍先完成类型、预算、硬主题和严格厂商过滤。过滤后的候选先按当前轮的可验证偏好排序，再按会话偏好分数、价格和商品 ID 排序。这样，偏好可以影响同质候选的选择，却不能使不满足预算或主题的商品重新进入结果。

组合购买以 `BundleLineItem` 表示一条独立需求，而不以“mug + shirt”这一固定结构表示。每条行项目带有类别、数量与本行主题条件。合计预算搜索在候选空间不超过配置阈值时穷举，在较大空间采用固定候选池与束宽控制计算量；Trace 公开记录候选空间、搜索策略、已检查组合数和可行组合数。该设计可扩展到重复类别或新增类别，但在有界搜索模式下的结果应理解为“已核验的可行组合”，而非未经说明的全局最优组合。

收藏、模拟订单和偏好档案以会话标识为键保存在当前设备的 `local_state/` 中。写入内容只有商品 ID、模拟订单行、状态、总价和派生的目录偏好；不会保存聊天原文、模型回复、密钥或支付信息。该机制用于演示会话连续性，不能替代账户、权限控制、服务端订单数据库或跨设备同步。

### 6.1 典型缺陷与改进价值

早期人工审查发现四类有代表性的问题：能力介绍可能夸大交易能力、混排主题可能未进入硬过滤、无结果的放宽说明可能自相矛盾、以及明确开放式请求可能仍进入探索。四个问题均被转化为最小范围的代码修复和自动化回归测试。该过程说明，Agent 质量不能只用“最终推荐碰巧正确”衡量；计划、状态和验证依据应共同正确，才能保证结果在不同商品排序下仍可靠。

### 6.2 人工回归发现的路由缺口及闭环

人工测试曾定位两条路由缺口。其一，目录查询使用只读分支后，活动 `ShoppingRequirement` 的事件与 `TaskContext` 虽会保留，但用户仅输入“给我推荐一个”时，系统未必复用当前选购条件。修复后，只有在 `active_task=selection`、已有商品类型且输入严格匹配中英文泛化直推短语时，代码才生成 `selection_mode=explicitly_open` 的合并计划；它复用已有类型、主题、预算和厂商，而不会把新条件误当作旧状态。

其二，“`mug 和 shirt 分别有什么价位？`”属于两类独立的只读事实查询，不是组合购买。修复后，组合购买检测优先处理含购买/推荐动词的输入；无购买意图的双类型价位问题则直接按类型分别统计数量、最低价和最高价，并以表格呈现。两条路径均不调用模型，也不会改写活动选购状态；已加入中英文离线回归。

### 6.4 系统演进与工程化（后续迭代）

在核心 Agent 工作流验证通过后，项目进行了系统性工程化演进，从「Streamlit 原型」升级为「Vue3 + FastAPI 生产式架构」，并补齐了电商闭环所需的完整链路：

1. **前端重构（Vue3 + TypeScript + Tailwind）**：从 Streamlit 单页改为 Apple 风三栏布局（左导航 + 对话工作区 + 商品详情栏），支持商品图片展示、毛玻璃（Liquid Glass）视觉、流式加载与响应式设计。

2. **服务端 API 化（FastAPI）**：将 Agent 封装为 REST API（24 个端点），前端与 Agent 解耦，支持 `/images`、`/avatars` 静态资源。

3. **用户认证（JWT + bcrypt）**：注册/登录，密码 bcrypt 哈希存储，JWT 无状态认证，支持角色（user/admin）。

4. **电商闭环**：收藏（影响推荐排序的偏好信号）、购物车（增删改查）、订单（`confirmed → shipped → delivered / cancelled` 状态机），均持久化到 SQLite。

5. **游客链路**：打开进入登录页，游客可用商品库浏览和购物对话，收藏/购物车/订单需登录，符合主流电商的权限边界设计。

6. **数据持久化统一**：将原先分散在内存和 JSON 文件的对话记录、会话状态、收藏、模拟订单统一到 SQLite 数据库（`conversations` 表存完整会话状态，`users`/`store` 表存账号与业务数据），解决后端重启数据丢失问题。

7. **管理员后台**：订单管理（跨用户发货/送达）、用户管理、商品查看。

8. **模型鲁棒性增强**：真实 DeepSeek API 测试暴露了 mock 测试无法发现的模型输出不稳定性（字段名漂移、非法 JSON、工具调用格式误解），针对性实现了 JSON 容错（中文引号/截断/子串提取）、TurnPlan 归一化（字段名/target/catalog_operations 容错）和 prompt 强化，将 service_error 从约 16% 降到约 6.5%。

9. **LLM Provider 抽象**：定义 `LLMProvider` ABC，支持未来接入多模型；模型熔断器与可观测性（不含 prompt 文本）。

10. **测试体系**：离线单元测试从 145 项增至 156 项（含 11 项鲁棒性容错测试），并新增 63 条真实 API 手动测试样例，实现「mock 测逻辑 + 真实 API 测鲁棒性」的双层验证。

### 6.5 最终定型：做减法

在补齐电商闭环之后，项目经历了一次收敛式重构，最终定型为「轻量、单一」的架构。演进并非单纯的功能叠加：初版原型先验证「模型做受限规划、代码做目录事实与决策」的核心思路，工程化阶段补齐认证、存储与业务闭环，最后阶段则反向删除了三个在购物单轮场景中价值不足的组件，使系统回到最简必要形态。

移除的三类组件及理由如下：

1. **RAG（embedding 向量检索）被 LLM 语义归一化替代。** 早期曾引入 bge-large 嵌入与语义检索，试图以向量相似度召回主题相近商品。实测表明该路径难以承载模糊主题的映射：以「小清新」为例，嵌入相似度最高仅约 0.51，无法可靠命中目录中的 `Nature` 标签；而 DeepSeek 在规划阶段即可将其语义归一化到 `Nature`。既然模型规划输出已承担主题语义映射，再叠加一层向量检索只会引入冗余计算与索引维护成本，而不带来增量收益，故予移除。

2. **ReAct 循环与 LangGraph 编排被移除。** 多步推理循环适用于需要逐步探索与收敛的开放任务；但购物场景的核心链路「需求理解 → 检索 → 硬过滤 → 确定性排序」是单轮规划加确定性代码即可完成的封闭流程，不依赖模型在运行时反复观察、行动与反思。ReAct 多步循环在此只增加时延、复杂度与失败面，未转化为购物效果，故予移除。

3. **双模式切换（智能推荐 / 深度对话）被移除。** 该设计把底层实现差异直接暴露给用户，要求用户先判断自己需要哪种模式，既增加理解负担，又使「深度对话」所依赖的 ReAct 在移除后失去存在依据。Agent 应当自行判断处理方式，而非把技术选择外包给用户，故予移除。

做减法后的最终架构收敛为四条核心路径：**LLM 语义归一化**（DeepSeek 在规划阶段将模糊主题映射为目录标签，如「小清新」→`Nature`）、**TurnPlan 单轮规划**（模型输出可校验的回合计划）、**确定性检索排序**（目录接地 → 硬过滤 → 偏好/价格/ID 稳定排序）、**个性化推荐**（以可解释理由呈现，如「为什么推荐它：它是 Nature 主题」，并结合收藏形成的偏好信号）。系统的智能体验——个性化推荐理由、主动对话引导、多轮记忆、无结果贴心处理、比较能力、收藏同步排序、上下文摘要压缩——均建立在这四条路径之上，而不再依赖被移除的组件。

从测试看，做减法后的系统仍保持正确性：180 项测试全绿（145 项核心逻辑 + 11 项鲁棒性容错 + 24 项认证/存储/对话状态），真实 DeepSeek API 测试覆盖模糊主题、多轮、送礼与无结果等场景均通过。删除未增加功能、也未损害已验证能力的组件，是本轮收敛的主要工程收益。

## 7. 局限性与后续工作

1. 商品数据为英文演示目录，中文别名和模糊主题的覆盖度仍有限；复杂表达可能需要更系统的实体规范化。
2. 系统已接入用户账户、购物车、模拟订单、收藏（均持久化到 SQLite），但未接入真实支付、库存预占、物流、退换货等服务端能力，因此真实支付/履约动作仍只能诚实拒绝；订单为本地模拟，不构成履约记录。
3. 外部模型调用仍可能受网络、限流和响应格式影响；系统具备一次结构修复、SDK 重试、短暂熔断和不含原文的调用指标，但不能消除服务时延或替代生产监控平台。
4. 当前系统可在用户明确要求时生成多行组合方案，支持每件预算和合计预算的代码验证；候选空间较大时为控制计算量采用有界搜索，因此不承诺跨组合的全局最优。若要用于真实选购，还需引入库存、价格实时性、商品相容性、配送和业务排序目标。
5. 当前主动引导基于目录统计和固定策略；会话偏好只来源于明确收藏/模拟订单。若接入跨会话点击、收藏或购买反馈，应增加身份认证、用户授权、数据保留策略、可撤回机制和偏差评估。
6. 当前多类型只读查询仅覆盖“分别询问价位”的并列统计；若后续支持多类型标签、厂商或交叉分面查询，仍需引入更通用的多作用域目录查询数据结构。

## 8. 结论

本项目最终定型为一条「轻量、单一、诚实」的架构路径：模型只做受限语义规划，代码只做目录事实与决策，两者之间不保留冗余的中间层。DeepSeek 在规划阶段完成语义归一化（如将模糊主题「小清新」映射为目录标签 `Nature`），输出可校验的 `TurnPlan`；本地代码随后执行目录接地、硬约束过滤与确定性排序（当前轮偏好 → 会话偏好 → 价格 → 商品 ID），并以可解释理由呈现推荐结果。多轮记忆、主动对话引导、无结果贴心处理、比较能力、收藏同步排序与上下文摘要压缩等智能体验，都建立在这条核心路径之上，而不依赖额外的检索或推理组件。

与初期的多组件方案相比，最终架构通过「做减法」收敛到必要组件：RAG 向量检索因被 LLM 语义归一化替代而移除，ReAct 循环与 LangGraph 因购物单轮场景用不上而移除，双模式切换因把技术细节暴露给用户而移除。移除之后，系统仍保持 180 项测试全绿（145 项核心 + 11 项鲁棒性 + 24 项认证/存储/对话状态），真实 API 测试覆盖模糊主题、多轮、送礼与无结果场景均通过，说明删除的是冗余而非能力。

系统「诚实」的一面体现在两处：其一，凡不能从 `products.jsonl` 复核的类型、预算、主题与厂商条件，系统明确报告不可满足，而不生成看似合理的商品；其二，真实下单、支付与取消因未接入履约服务而由能力注册表诚实拒绝，收藏与模拟订单被明确限定为本地会话记录，形成可解释的弱排序信号，而不伪装成真实交易。后续工作可评估更通用的多类型查询、带库存与相容性约束的组合优化、账户级个性化与真实订单能力，而不应把尚无执行器的交易操作伪装为可用功能，也不应重新引入已被证明冗余的组件。
