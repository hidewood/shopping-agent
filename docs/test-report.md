# 智能购物 Agent 测试报告

## 1. 测试目标与判定原则

本报告验证系统是否按照题目要求完成需求理解、商品搜索、候选比较、约束检查、购买决策和结果说明；同时核验多轮对话、主动引导、失败处理和界面呈现是否可靠。测试只认可 `products.jsonl` 中可验证的事实，不以模型的自然语言说明替代目录校验。

每条用例按以下五项判定：

1. **路由正确**：聊天、目录查询、详情、比较、推荐和交易请求不相互误判；
2. **状态正确**：补充条件合并，明确换类时替换，只读查询不污染选购状态；
3. **事实正确**：商品 ID、价格、厂商和标签均来自本地目录，且满足全部硬约束；
4. **对话自然**：用户可逐步补充条件；系统在信息不足时说明下一步可补充什么；
5. **边界诚实**：无结果、未知主题、模型异常和未实现交易不伪造成功。

商品库包含 1,740 件商品：`mug` 与 `shirt` 各 870 件。除特别说明外，人工用例均应点击“新建对话”后独立开始。

## 4. 扩展回归场景

除 A1–A18 外，以下场景用于覆盖复杂状态迁移与边界。它们可作为答辩或发布前复测清单。

| 组别 | 场景 | 通过标准 |
| --- | --- | --- |
| H1 | mug → Ocean 10–20 → 12–18 且优先厂商 | 新区间替换旧区间，偏好只参与排序。 |
| H2 | 选购中查询总体价位，再更新预算 | 只读查询后仍保留原类型和主题。 |
| H3 | 选购 → 商品比较 → 再调预算 | 比较不清空选购状态。 |
| H4 | 有效区间后输入倒置区间 | 倒置区间只返回澄清，不继续推荐。 |
| H5 | 硬厂商与软主题偏好同时出现 | 硬条件过滤，偏好不导致零结果。 |
| H6 | `not a mug` / `不要杯子` 后改为 shirt | 旧类别与条件不残留。 |
| H7 | 礼物 → 类型 → 主题与预算 | 首轮只询问类型，后续完成推荐。 |
| H8 | 先统计 Ocean mug 数量，再要 <$20 推荐 | 统计为只读，推荐继承上下文。 |
| H9 | 详情 → 下单 → 比较 | 拒绝交易后仍可正常比较。 |
| H10 / C10 | 同轮出现 mug 与 shirt | 提示分别处理，不创建不存在的混合类型。 |
| C5 / C6 | 更换主题；撤销预算并增加偏好厂商 | 正确替换主题、清除预算、保留未修改条件。 |
| C7 | `$9.99` 边界与严格小于 | `≤ 9.99` 可命中，`< 9.99` 无匹配。 |
| C8 | 已筛选条件下统计，再收紧预算 | 统计与后续推荐均使用活动选购状态。 |
| C11 | 提示注入式“忽略之前条件” | 不绕过类型澄清或目录核验。 |
| C12 | 类型、主题、硬厂商、预算、软主题组合 | 只选择满足全部硬条件的商品，并披露未命中偏好。 |

## 5. 界面验收要点

1. 用户发送消息后，消息应立即出现在对话中；模型请求期间显示“正在分析需求…”。
2. 推荐结果顺序应为：Agent 文字回复 → 已应用条件 → 商品卡片 → 可折叠核验依据。
3. 探索样例必须标明“目录样例”，不能误称为最终推荐。
4. 价格区间摘要应显示为 `USD 10.00 ≤ 价格 ≤ USD 20.00`，字体一致，不出现数学公式样式。
5. 商品库浏览页的搜索、类型筛选和分页不应改写推荐页会话状态。

## 6. 失败记录应包含的证据

若人工复测发现问题，应记录：完整消息顺序、截图文件名、推荐商品 ID、页面“已按以下条件筛选”文字，以及“核验依据”中的 Trace。Trace 可区分问题发生在模型规划、状态归约、目录接地、检索过滤、排序还是 UI 展示。
